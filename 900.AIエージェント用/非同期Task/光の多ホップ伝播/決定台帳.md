# 光の多ホップ伝播 — 決定台帳

## D-001 伝播ロジックの配置

`UActorComponent` / 専用汎用クラスは新設せず、現行の `AColoursLightSourceBase` の内部処理として実装する。

理由: 現時点の利用箇所は光源基底の候補点判定のみで、独立Componentの状態・Tick・再利用先が存在しないため。

## D-002 可視性判定方式

形状判定で候補になった点にだけ `LineTraceMultiByChannel` を1本撃つ。光源から放射状にレイを扇状発射する方式はゲームプレイ判定には使用しない。

## D-003 複数ガラスの扱い

Stage1では反射・屈折がなく進行方向が変わらないため、ガラスごとの出射点再Traceは行わない。候補点までの1本のMulti Trace上で、手前から順にガラスの透過率を累積適用する。

## D-004 Collision Channel

既存 `ECC_GameTraceChannel2` はCone断面表示用のDetectionBox Block / Segment Ignoreという特殊設定に依存しているため、可視性判定へは流用しない。

光のゲームプレイ可視性専用Trace Channelを1本だけ追加する。これは既存機能で要件を満たせない具体的理由があるため、車輪の再発明には該当しない。

- 通常の遮蔽物: Block
- `AErasableWall` の有効Segment: Block
- `AErasableWall` のDetectionBox: Ignore
- 消去済みSegment: Collision無効のため非ヒット
- ガラス: Overlap
- Pawn/Character: 既存挙動に合わせて光遮蔽対象外

## D-005 ガラス抽象化

`IColoursTransmissive` や汎用Transmittance Componentは作らない。Stage1で透過する具体物はガラスのみなので、具体的なガラスクラスから透過率を取得する。

二種類目の透過物が実際に必要になった時点でInterface抽出を再検討する。

## D-006 ガラスの最小責務

SCRUM-72でE2E検証に必要な最小限として、具体的なガラス実装が未存在なら、Collisionと透過率を持つ最小の `AColoursGlass` を追加する。見た目・演出・アセット作り込みはガラス側Taskへ残す。

## D-007 色変換

ガラス透過率を `(T_R,T_G,T_B)`、入射RGBを `(R,G,B)` とする。

1. `P=(R*T_R, G*T_G, B*T_B)`
2. `M=max(P_R,P_G,P_B)`
3. `M≈0` なら吸収として黒
4. それ以外は `RGB'=round(255 * P / M)`

`Intensity` と `DamageValue` は変更しない。複数ガラスではこの変換を手前から順に適用する。

## D-008 対象Actor自身の扱い

候補点への可視性Traceでは、判定対象Actor自身をQueryから除外する。

理由: 対象Segmentが前tickで消去済みだとCollisionが存在せず、対象自身へのヒット有無を到達条件にすると照射/復元が振動するため。対象点までに他のBlockが無ければ到達とみなす。

## D-009 既存ConeTrace

`AColoursConeLight::PerformConeTrace()` の扇状Traceは、SCRUM-73で残した断面表示の互換フォールバックとして当面維持する。ただしセル照射・色搬送のゲームプレイ判定には使用しない。

## D-010 非対象

- 反射
- 屈折
- 出射面計算API
- 再帰/再Trace式の真のセグメント伝播
- 将来用汎用Propagation Framework
- 将来用Interface/Component

必要になった時点で別Taskとして追加する。
