# Colours プロジェクト 立ち上げ・運用整備 PRD

## 概要

これは UE ゲーム「Colours」（光と色で解くアクションパズル）の
チーム運用・プロジェクト立ち上げに関するタスク管理ドキュメントです。

担当: Mori（C++・設計）＋ Hiruta（レベル配置・プレイテスト）の二人体制。
バージョン管理: Diversion（Content を含むプロジェクト全体）を正式採用。

このドキュメントの対象は「立ち上げ・運用の整備タスク」のみです。
実装バックログ（Step6.1〜11・壁消去アーキテクチャ決着等）は対象外です。

---

## タスク 1: ドキュメント閲覧・共有方法を確定する

### 目的
Hiruta が仕様・実装ログ・タスクをどうやって読むかを決め、両者が同じドキュメントを参照できる状態にする。

### 背景
仕様・実装ログは Vault（Obsidian, Diversion shared リポジトリ）に置かれているが、
Hiruta が実際にどこ経由で読むかは明文化されていない。

### 成果物
- Vault 閲覧手順の明文化（CONTRIBUTING.md か専用 ONBOARDING.md に追記）
- Hiruta が読むべきドキュメント一覧（最低限: 仕様/00〜04・CONTRIBUTING.md）

### 推奨デフォルト（たたき台）
Vault 用 Diversion (shared) を Hiruta のローカルに同期 → Obsidian で閲覧。

### 受け入れ条件
Hiruta が仕様・タスク・実装ログにアクセスできることを口頭または画面共有で確認できること。

---

## タスク 2: コミュニケーション・同期リズムを決める

### 目的
二人の進捗共有・決定記録の運用ルールを明文化し、決定がどこにも残らない状態を防ぐ。

### 背景
現在 `決定ログ.md` は Mori が追記しているが、定例頻度・連絡手段・Hiruta の報告先は未定義。

### 成果物
- 定例頻度・連絡手段・決定記録運用の合意
- CONTRIBUTING.md または `コミュニケーション方針.md` への記載

### 推奨デフォルト（たたき台）
週1回（土または日）の簡易同期 + 都度の `決定ログ.md` 追記。
連絡は Discord か LINE（どちらか使いやすい方）。

### 受け入れ条件
定例の場（曜日・時間帯・ツール）と決定記録の置き場が合意文書に記載されていること。

---

## タスク 3: 各人の作業計画を立てる

### 目的
ロードマップから今後 2〜4 週分の担当範囲を人別に割付け、
「誰が何週に何をするか」を可視化する。

### 背景
ロードマップ・月目標は存在するが、Hiruta 側の具体的な週次行動が未定義のまま。
Hiruta は Lv0（サンドボックスで慣れる）から始める想定だが、
その期間がどのくらいかも決まっていない。

### 成果物
- 2〜4 週分のスプリントプラン（誰が・何を・いつまでに）
- Vault 週目標ファイルまたは dedicated プランファイルへの記載

### 推奨デフォルト（たたき台）
- Hiruta: 第1週 Lv0（サンドボックス）→ 第2週以降 Lv1（サブレベル担当）
- Mori: 実装バックログの優先度 A（Step7〜9）を並行して進める

### 受け入れ条件
両者の今後 2 週分のタスクが文書化されていること。

---

## タスク 4: Hiruta にやってみたいことをヒアリングする

### 目的
Hiruta のモチベーション・興味・スキル習得目標を把握し、
タスク割付・学習パスの設計に活かす。

### 背景
Vault `やることリスト.md` に明記されている未着手項目。
二人開発を長続きさせるためにも、Hiruta が「やってみたい」と思える作業を把握する。

### 成果物
- Hiruta の興味・やりたい領域のヒアリングメモ（Vault または CONTRIBUTING.md に追記）
- 結果を踏まえた Lv0〜Lv2 の優先順位見直し（必要な場合）

### 推奨デフォルト（たたき台）
口頭ヒアリングをセッション内で行い、結果を `決定ログ.md` または専用メモに記録。

### 受け入れ条件
Hiruta の関心領域が Vault に記録されていること。

---

## タスク 5: アセット命名規約を策定・文書化する

### 目的
Hiruta が Content 内にアセットを作成・配置するとき、
命名が統一され後から探しやすい状態にする。

### 背景
現在は命名規約が存在せず、Hiruta が配置を始めると Content が混在する恐れがある。
Hiruta が Lv1（具体配置）に移行する前に整備が必要。

### 成果物
- アセット命名プレフィックス規約（例: BP_ / M_ / SM_ / L_ / T_ 等）
- フォルダ構成規約（例: Content/Gimmick/ / Content/Characters/ 等）
- CONTRIBUTING.md または `アセット規約.md` への記載

### 推奨デフォルト（たたき台）
UE 公式推奨に準拠（Blueprint=BP_, Material=M_, StaticMesh=SM_, Level=L_, Texture=T_）。

### 受け入れ条件
CONTRIBUTING.md か専用規約ファイルに命名規約が記載されていること。
Hiruta が確認済みであること。

---

## タスク 6: コーディング規約を明文化する

### 目的
Mori の C++ 実装スタイルを文書化し、将来の参照・一貫性維持・Mori 以外の作業引き継ぎを可能にする。

### 背景
現状「既存コードに合わせる」という暗黙ルールのみ。
Diversion のコミットメッセージ規約も実態はあるが未明文化。

### 成果物
- C++ 命名規約（クラス/変数/関数/マクロ）、フォルダ構成方針
- UE 固有の規約（UPROPERTY/UFUNCTION の使い方方針等）
- Diversion コミットメッセージ規約（推奨: conventional commits 形式）
- `コーディング規約.md` として `docs/` または `Source/Colours/` 配下に作成

### 推奨デフォルト（たたき台）
UE C++ 公式スタイル + conventional commits（feat / fix / refactor / docs + スコープ）。

### 受け入れ条件
規約ドキュメントが作成されていること。

---

## タスク 7: LICENSE 方針とサードパーティライセンス管理を決める

### 目的
プロジェクトの著作権・ライセンスを明確化し、
使用しているアセット・プラグインのライセンス違反リスクを排除する。

### 背景
現在リポジトリに LICENSE ファイルが存在しない。
また使用アセット（Marketplace 購入品等）のライセンス台帳も未整備。

### 成果物
- ソースコードのライセンス方針（公開 or 非公開に応じて選択）
- 使用アセット・プラグインのライセンス台帳（`docs/LICENSES_THIRD_PARTY.md` 等）

### 推奨デフォルト（たたき台）
個人/小規模プロジェクト・非公開なら All Rights Reserved（LICENSE ファイル不要でも可）。
Marketplace アセットは「Epic Games EULA 準拠」を記録するだけでも可。

### 受け入れ条件
ライセンス方針が決定・記録されていること（LICENSE ファイル or docs への記載いずれか）。

---

## タスク 8: UE エンジンバージョン固定と更新方針を決める

### 目的
UE バージョンアップ時の判断基準を事前に合意し、過去のような 5.8→5.3 ダウングレードのような混乱を防ぐ。

### 背景
過去に UE5.8 から UE5.3 へのダウングレードがあり、アセット消失等の痛みを経験している。
現在は UE5.3 固定で運用中だが、バージョン変更の判断基準が未定義。

### 成果物
- 現行バージョン（UE5.3）固定の合意と記録
- UE バージョン変更の判断基準（変えて良いトリガー / 変えてはいけない条件）
- `README.md` への現行バージョン明記（既存の記載を確認・更新）

### 推奨デフォルト（たたき台）
Phase1 完了まで UE5.3 固定。変更は Phase 間の区切り（マイルストーン後）に限定。
変更前に必ず Diversion でフルバックアップを取る。

### 受け入れ条件
バージョン方針が `決定ログ.md` または README に記録されていること。

---

## タスク 9: プラグイン管理方針を決める

### 目的
使用プラグインの一覧を管理し、PIE クラッシュ等の問題が起きたときに原因を素早く特定できるようにする。

### 背景
過去に SequencerAnimMixerToolset（MCP プラグイン）が ControlRig と干渉して PIE クラッシュを起こした実績がある。
どのプラグインを有効化しているかの台帳が存在しない。

### 成果物
- 現在有効なプラグイン一覧（名前・用途・追加理由）
- プラグイン追加時のルール（追加前に用途・リスクをチームに共有 + Diversion コミット）
- `docs/PLUGINS.md` または README への記載

### 推奨デフォルト（たたき台）
追加・削除は Mori がオーナーとなり、`決定ログ.md` に記録。
PIE クラッシュが発生したら最新プラグイン変更を最初に疑う。

### 受け入れ条件
プラグイン一覧ドキュメントが存在し、追加/削除ルールが記載されていること。

---

## タスク 10: バックアップ・冗長化方針を決める

### 目的
Diversion クラウド以外のバックアップ手段を確定し、クラウド障害・誤削除時のリカバリーリスクを下げる。

### 背景
README に「バックアップは Dropbox 等を案内」と記載があるが、
実際に運用されているかは未確認。Diversion クラウドのみに依存している可能性がある。

### 成果物
- バックアップ方針の合意（Diversion クラウド + ローカル/外部媒体の組み合わせ）
- バックアップ頻度・責任者の明記
- README または `docs/BACKUP.md` への記載

### 推奨デフォルト（たたき台）
Diversion クラウド（日次自動）＋ Mori が週1で外部 HDD or Dropbox にローカルコピー。

### 受け入れ条件
バックアップ手段と頻度が文書化され、実際に運用が始まっていること。

---

## タスク 11: プレイテスト・バグ報告フローを定義する

### 目的
Hiruta がバグや違和感を発見したとき、どこにどう報告すればよいかを明確にし、
バグが放置されずに Mori がトリアージできる状態にする。

### 背景
CONTRIBUTING.md では「バグや違和感を Mori に報告する」とのみ記載されているが、
具体的な報告方法・テンプレートが存在しない。

### 成果物
- バグ報告テンプレート（再現手順 / 期待動作 / 実際の動作 / スクリーンショット）
- 報告先（タスク管理ツール or 共有メモ or 口頭 + 事後記録）
- トリアージ担当（Mori）とレスポンス目標の明記
- CONTRIBUTING.md または `docs/BUG_REPORT.md` への記載

### 推奨デフォルト（たたき台）
報告先は タスク管理ツール（後日決定）のバグカテゴリに起票。
緊急の場合は Discord/LINE で連絡後に起票。

### 受け入れ条件
報告テンプレートと報告先が CONTRIBUTING.md または専用ドキュメントに記載されていること。

---

## タスク 12: ドキュメント整合・ハウスキーピングを行う

### 目的
既存ドキュメントの不整合・廃止済み記述を修正し、
新しいチームメンバーが迷わずに情報を参照できる状態にする。

### 背景
以下の不整合が確認されている:
- `docs/Architecture/` フォルダが空のまま残存（実体は `Source/Colours/Public/<カテゴリ>/` 配下に移動済み）
- Vault `_現在地.md` のリポジトリパスが `D:\UEProjects\Colours`（旧）のまま（実体は `E:\UEProjects\Colours`）
- README・ARCHITECTURE.md が旧パス（`docs/Architecture/`）を参照している可能性
- バージョン管理の記述が Git/Diversion 混在になっている箇所がある可能性

### 成果物
- `docs/Architecture/` 空フォルダの整理（削除または用途明記）
- `_現在地.md` のパス修正（`D:` → `E:`）
- README・ARCHITECTURE.md の参照リンク確認・修正
- バージョン管理の記述を Diversion 正式採用に合わせて統一

### 受け入れ条件
上記4点の不整合が解消されていること。
README 記載のセットアップ手順で Hiruta が迷わないこと。

---

## タスク 13: チームゲーム開発の作業種別カタログを作成する

### 目的
「チームでのゲーム開発・プロジェクト立ち上げで一般的に発生する作業」を一覧化し、
今後の計画立案・役割分担の参照資料とする。

### 背景
Vault `やることリスト.md` に「作業の種類のリストアップ（このプロジェクトに依存しない、
チームでのゲーム開発・プロジェクト立ち上げにおいて一般的に発生する作業）」が未着手のまま残っている。

### 成果物
- 作業種別カタログ（企画 / 仕様 / 実装 / デバッグ / テスト / 運用 / リリース に分類）
- 各作業種別に対して Colours での担当（Mori / Hiruta / 共同 / 未定）を付記
- Vault または `docs/` への保存

### 推奨デフォルト（たたき台）
本 PRD から生成されたタスク群を起点に一般化したカタログを作成。
後から新しい作業種別が見つかったら追記する運用とする。

### 受け入れ条件
作業種別カタログが Vault または docs/ に存在し、主要作業種別が網羅されていること。
