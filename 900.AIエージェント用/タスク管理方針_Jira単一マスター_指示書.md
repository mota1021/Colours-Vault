# タスク管理方針 — Jira単一マスター

## 現行方針

- タスクの状態・依存・担当の正本は Jira (SCRUM) のみ。
- ChatGPT Work など、接続済みJiraを直接読み書きできる環境では、**Jiraを直接参照することを標準**とする。`チケットスナップショット.md` を状態判断の入力に使わない。
- タスクの着手・完了・依存・担当などを変更する必要がある場合は、対象と変更内容が今回の作業範囲として明確なら、Work の接続済みJira操作から直接反映する。
- Work からJiraを直接操作できない場合だけ、承認済みのローカル write-through 経路（`jira_task_update.py` 等）をフォールバックとして使う。
- ローカルに第二のタスク台帳や双方向同期状態を持たない。

## 識別

識別規約の正本は [[タスク識別ルール]]。

- 会話・文書・ファイル名では意味名を優先する。
- Jira API、依存関係、外部操作では Jiraキーを使う。
- 旧独自短縮IDおよび `元ID:*` ラベルを運用上の識別子として使用しない。

## スナップショット

`shared/900.AIエージェント用/チケットスナップショット.md` は、Jiraを直接参照できない環境向けの**フォールバック用キャッシュ**であり、日常のタスク状態判断の標準入力ではない。

- Jiraへ直接アクセスできる場合は、スナップショットよりJiraの現在値を優先する。
- スナップショットが古い、取得日時が不明、または現在地・実装実績と食い違う場合は、着手可否・完了・依存・担当の判断に使わない。
- 必要時のみ `shared/.vault-data/900.AIエージェント用/scripts/jira_sp_snapshot.py` で再生成する。
- スナップショットは使い捨ての派生物であり、Jiraと競合する正本ではない。
- `着手開始日` のみVault側ユーザー管理値として Jiraキーで引き継ぐ。

## Workでの標準運用

1. 作業開始時に、対象タスクのJira現在値を直接確認する。
2. Vault / GitHub / Diversion の実績とJiraが食い違う場合は、実績の根拠を確認してからJiraを更新する。推測で状態を進めない。
3. 作業中に状態変更が必要になった場合は、今回合意した範囲だけJiraへ反映する。
4. 作業終了時に、Jiraの状態・依存・担当が実際の進捗と一致しているか確認する。
5. スナップショット更新は、直接Jiraを参照できない後続環境へ渡す必要がある場合だけ行う。

## 外部操作

- Jiraの大量変更は対象・変更内容・件数を先に提示し、明示承認後に実行する。
- 起票・削除・依存リンク・状態変更は今回合意した対象だけに限定する。
- API失敗時は成功・失敗・未処理を分け、推測で継続しない。

## 履歴

2026-07-06のTaskMaster不採用、Jira単一マスター決定、および旧独自ID前提の移行手順は archive の旧指示書を履歴として参照する。2026-09-16以降は、Jiraへ直接接続できる環境では直接参照・更新を標準とし、スナップショットはフォールバック用途に限定する。
