# 実装: 光の伝播

## クラス方針

- 伝播処理は、SCRUM-73で導入済みの `AColoursLightSourceBase` 内部へ追加する。
- 専用 `UActorComponent` / 汎用Propagationクラスは作らない。現時点の利用箇所が光源基底しかなく、独立ライフサイクルや状態を必要としないため。
- Stage1で透過する具体物はガラスだけなので、`IColoursTransmissive` 等の将来用Interfaceも作らない。
- ガラスの表裏を別オブジェクトとして扱わない。

## 伝播処理

- 発射は狙い撃ち方式の2段階で行う。
  1. `GetLightBounds()` / `IsPointLit()` で候補点を絞る。
  2. 光源位置→候補点へ `LineTraceMultiByChannel` を1本実行し、遮蔽と透過を解決する。
- ガラスは専用Light Visibility Trace Channelに対してOverlap、通常遮蔽物はBlockとする。
- Multi Traceで取得したガラスを光源に近い順に処理し、`FColoursLightValue` のRGBへ透過率を累積適用する。
- 反射・屈折が無いStage1では方向が変わらないため、ガラス裏面の出射点取得や再Traceループは実装しない。
- 透過後RGBが黒、または `Intensity <= 0` なら候補点へは光が届かない。
- 候補Actor自身はTrace QueryでIgnoreする。対象セルが既に消えてCollisionが無い場合でも、前tickとの照射状態が振動しないようにする。
- 一巡単位で全候補を再計算し、途中経路は永続保持しない。

## Collision Channel

- 既存 `ECC_GameTraceChannel2` はCone断面表示用として `DetectionBox=Block / Segment=Ignore` に依存しているため、Gameplay可視性判定へは流用しない。
- 光のGameplay可視性専用Trace Channelを1本だけ追加する。
- `AErasableWall` は、有効SegmentをBlock、DetectionBoxをIgnoreとする。Segment消去時はCollision自体が無効になるため、穴越しに奥へ光が届く。
- Character / Pawnは既存Cone挙動に合わせて遮蔽対象外とする。

## ガラス

- 実装開始時点で具体クラスが無い場合、E2E検証に必要な最小限の `AColoursGlass` を追加する。
- 必須責務はCollisionと `Transmittance (T_R,T_G,T_B)` の保持のみ。
- プレイヤーに対しては壁としてBlock、Light Visibility ChannelにはOverlapする。
- ガラス演出、完成アセット、反射、屈折、出射点APIはこのTaskに含めない。

## 判定フロー

1. 光源が `GetLightBounds()` で候補壁を絞る。
2. 壁からセル中心を得る。
3. `IsPointLit()` で形状内か判定する。
4. 形状内なら候補点までMulti Traceする。
5. 途中のガラスOverlapを順番に色変換する。
6. 途中に非透過Blockがあれば不達。
7. 到達した透過後 `FColoursLightValue` を壁へ通知する。
8. 壁側の色一致ゲートはSCRUM-20で接続する。

## 既存ConeTrace

- `AColoursConeLight::PerformConeTrace()` の放射状Traceは、SCRUM-73で既存断面表示を維持するための視覚フォールバックとして当面残す。
- Gameplayのセル照射・色搬送には使用しない。
- このTaskで削除すると断面可視性の代替判定まで必要になり、現在要件を超えるため削除しない。

## 外部化パラメータ

- 透過率 `(T_R,T_G,T_B)`: ガラス側に保持。
- 更新周期は既存Coneの0.05sを維持する。新しい負荷調整パラメータやグループ分割は追加しない。

## 実装原則

- UE標準Trace / Collision機構を優先する。
- 将来の反射・屈折だけを理由に抽象化を先行させない。
- 二種類目の透過物、反射、屈折など具体的な追加要件が発生した時点で、Interfaceや独立Propagationクラスへの抽出を再検討する。
