# 仕様規約

## 境界判定テーブル

どのファイルに何を書くかの判定基準。**1記述＝1行き先**で迷いなく決まる。

| 記述の種類 | テスト | 行き先 |
|---|---|---|
| 内部状態・ルール | 画面/音/操作を消しても残る規則か？ | `.020.仕様` |
| 知覚・操作する出力 | 感覚器官への出力（見た目・音・操作感）か？ | `.030.演出・UI` |
| 技術的な作り方 | 「どう実現するか」の話か？ | `.040.実装` |
| 定義・目的 | — | `.020.仕様` 冒頭「概要・目的」が唯一の正典 |
| 未決事項 | — | 各ファイルの `> 未決`（現行踏襲） |

### 記述しないこと（不在・否定の排除）

- **「〜はない」「〜は持たない」「特にない」等、不在・否定を宣言するだけの記述を仕様に書かない。** 書かれていなければ存在しない・作用しないと読めるため、不在の明示は冗長でむしろ混乱を生む。
- 打ち合わせで「無い／特にない」と確定した観点は、正式仕様には出さない。該当セクションが空になる場合はセクションごと省略する。
- 例外: 「意図的にしない」ことが設計判断として重要な場合（誤解を招く既定を打ち消す等）は、理由とセットで書いてよい。

### メカニクスの特性から創発する帰結は「仕様」にしない

- 既存メカニクスの性質から自動的に生じる帰結や、そこから生まれる遊びは、それ専用に実装する「仕様」ではない。**元メカニクスの特性**、または**それを活用するレベル設計**に属する。
- こうした帰結を仕様として書くと「それ用に何かを実装する」という誤った前提が生まれる。まして**別機能の仕様には書かない**。
- 判断テスト: 「これを実現するために専用の挙動・データ・処理を作る必要があるか？」→ **No（元の性質から自然に出る）なら仕様にしない**／Yes なら仕様にする。

### ラフの正本契約

`.010.ラフ` は、以下を時系列で保持する仕様策定の正本。

1. 人間が書いた初稿・追記
2. AIとの打ち合わせログ（質問・提案と、それに対するユーザー回答）

元の初稿は履歴として残し、AIが後から本文を整理・置換して辻褄を合わせない。

現在有効な内容を判定する際は、**後からユーザーが明示的に確定した内容を優先する**。AIの質問・提案だけでは仕様にならない。AI案に対してユーザーが承認した場合は、その提案と承認の組を確定内容として扱う。

初稿と後のログが矛盾していて、どちらが現在有効か明確でない場合は生成前の blocker として確認する。

### 生成時の原則（実体は固定・表現は整える）

ラフから 020/030/040 を生成・更新する際：

- **実体（事実・ルール・数値・条件・設計判断）はラフ全体から確定できるものだけを使う。** 追加・推測補完・旧正式ファイル・決定ログ・隣接仕様からの内容引継ぎは禁止。
- 決定ログや隣接仕様は、矛盾や影響範囲の確認には使ってよいが、ラフにない新しい仕様を生成物へ持ち込まない。
- **表現（文体・構造・順序・分割・言い換え）は読みやすさのために整えてよい。** 会話調・断片的なラフを仕様文体へ書き直したり、長文を箇条書きに分割したりしてよい。
- 新事実の追加か既述の言い換えか判断がつかない場合は、追加せず生成前に確認する。

## 仕様策定フロー

新規作成と既存仕様の更新を同じ流れで扱う。

1. **人間が `.010.ラフ` を書く。** 最初から完成させる必要はない。要件、アイデア、未決事項、実装方針の案を自由に混在させてよい。
2. `/colours-spec-interview` でAIがラフをレビューし、要件不足、曖昧さ、矛盾、境界条件、必要なら簡単な実装方針を対話で詰める。
3. 各対話の内容を、AIが `.010.ラフ` 末尾の `## 打ち合わせログ` へ時系列で追記する。質問・提案とユーザー回答の文脈が分かる形で残す。
4. 実装着手前に決めるべき blocker がなくなったら、`/colours-spec-from-rough` でラフ全体から `.020.仕様` / `.030.演出・UI` / `.040.実装` を**全再生成**する。
5. 既存の正式仕様は比較用であり、ラフにない内容を差分更新で温存しない。
6. 出力ファイル（020/030/040）は直接修正しない。変更したい場合はラフへ戻り、必要な打ち合わせを経て再生成する。
7. 演出・UI や実装が **無い** 仕様は該当ファイルを生成しない（空ファイルを残さない）。
