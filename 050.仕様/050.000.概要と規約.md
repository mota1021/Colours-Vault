# 概要: [[Colours]]

## ゲーム概要
光と色で解くアクションパズル。

## 仕様ファイルのルール

各仕様は **5ファイル構成のフォルダ**（`050.001.テンプレート/` を参照）。
ファイル名は **`[意味名].[役割番号].[役割].md`**（意味名 = 自フォルダ名から `NNN.MMM.` 番号 prefix を除いた部分）：

| ファイル | 役割 | 編集者 |
|---|---|---|
| `[意味名].000.index.md` | 構成一覧・境界判定テーブル・運用フロー | 自動生成のまま触らない |
| `[意味名].010.ラフ.md` | 人間が書く初稿と、その後のAIとの打ち合わせログを残す仕様策定の正本 | 初稿・追記: 人間 / 打ち合わせログ追記: AI |
| `[意味名].020.仕様.md` | 内部ルール・挙動条件 | AI生成 |
| `[意味名].030.演出・UI.md` | 見た目・音・HUD | AI生成 |
| `[意味名].040.実装.md` | 技術的な作り方・実装ログへのリンク | AI生成 |

例: `020.020.モノを置く/` → `モノを置く.000.index.md` / `モノを置く.010.ラフ.md` / `モノを置く.020.仕様.md` …

- カテゴリ（プレイヤー/ギミック/ライト）は `[意味名].000.index.md` 1枚（子仕様一覧＋カテゴリ固有内容）
- 演出・UI や実装が **無い** 仕様は該当ファイルを生成しない

### 命名の制約（wikilink のため）

意味名を前置するのは、Obsidian の wikilink が **basename で解決する**ため。番号のみの名前（旧 `020.020.仕様.md`）は Vault 内で衝突し、どの仕様を指すか特定できなかった。basename を一意にすることで `[[モノを置く.020.仕様]]` と書ける。

- **意味名は Vault 内で一意にする。** 新規フォルダを切る前に既存の意味名と重複しないか確認する。
- **意味名に `.`（ドット）を使わない**（役割番号の区切りと衝突する）。`/ \\ : # ^ [ ] |` も不可。
- 詳細は [[ファイル命名・ディレクトリ規約]] §2.1 が正本。

## 仕様策定フロー

仕様の新規作成・更新を同じ流れで扱う。

1. **人間が `.010.ラフ` を書く。** 最初から完成させる必要はなく、やりたいこと、挙動、条件、未決事項、実装方針の案などを自由に混在させてよい。
2. **AIがラフをレビューし、不足・曖昧さ・矛盾を対話で詰める。** 必要に応じて簡単な実装方針も相談する。
3. **対話内容を `.010.ラフ` の末尾へ時系列の打ち合わせログとして追記する。** 元の初稿は履歴として残し、AIが勝手に書き換えて整合させない。
4. 打ち合わせが終わったら、**ラフ全体を正本として `.020.仕様` / `.030.演出・UI` / `.040.実装` を全再生成する。** 既存の正式仕様を差分更新して内容を温存しない。

ラフ内で初稿と後の打ち合わせ結果が食い違う場合は、**後からユーザーが明示的に確定した内容を現在の決定として扱う**。どちらが有効か判定できない場合は生成前に確認する。

詳細な対話手順は `/colours-spec-interview`、正式仕様の生成契約は `/colours-spec-from-rough` を正本とする。
